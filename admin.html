System Guide

Current operating guide for the IPGS Admission Command Center — master data, admission, SKY operations, Orientation, Academic Handover and student access.

CURRENT OPERATING GUIDE · SEP 2026
Operating model: the ACC combines several operational modules, but not every module is a hard gate for another. Admission workflow, Prospect / Activation, Orientation and Academic Handover each keep their own records and controls. Follow the rules inside the module being used and do not create an artificial cross-module block unless the system explicitly requires it.

Quick Module Map

What each area is for

Dashboard

  1. Monitor total workload, pending actions and funnel progress.
  2. Use Refresh when a newly completed action is not yet reflected.

Applications

  1. Main admission workflow.
  2. Open an applicant to review documents, screening, SAC / Assessment, Offer & Acceptance and Activity.
  3. Use the applicant Operational Action Center for the current next action.

SAC

  1. Create SAC sessions and assign candidates.
  2. Prepare the controlled SAC pack.
  3. Record authorised SAC decisions.

IA / PREREQ

  1. Track candidates routed to Internal Assessment.
  2. PREREQ follows IA only where required by the approved route.
  3. Complete the route before Offer.

Prospect / Activation

  1. Tracks consultant / Marketing completion of SKY Prospect setup.
  2. Registry records SKY activation separately.
  3. This module is operationally independent from admission stage.

Orientation

  1. Main page is for session monitoring.
  2. Click View Session for student roster, communication, attendance & feedback, recording, completion and activity.
  3. Completion generates the official Orientation report.

Academic Handover

  1. Main page is for handover-session monitoring.
  2. Click View Handover for students, communication, provisioning, Student Access and activity.
  3. Academic Handover is managed separately from Orientation.

Academic Consultants

  1. Maintain consultant / Marketing records.
  2. Use unique referral links for attribution.
  3. Do not overwrite an existing consultant when adding a new one.

Fee Structure

  1. Master source for agent Fee Group selection.
  2. Maintain programme, level, study mode, intake, fee components, payment schedule and approved PDF.
  3. Only ACTIVE structures appear to agents.

AI Operations Center

  1. Current control room for live workload visibility and agent ownership.
  2. AI agents shown as NOT ACTIVATED are monitoring / design placeholders only.
  3. Autonomous execution will be enabled module by module after testing and approval.

Reports

  1. Use operational distributions and funnel reporting.
  2. Export data when required for internal analysis.
  3. Session-specific official reports are viewed inside the relevant module.

System Guide

  1. Use this page as the current staff operating reference.
  2. When system behaviour changes, this guide must be updated together with the module.

End-to-End Operating Flow

Admission spine + parallel operational workstreams
Master data prepared before operational use
Academic Consultants+Fee Structure Master→Ready for Application / Prospect Operations
01
Application Submitted
→
Student Completes the online Admission Form and uploads the four compulsory documents: IC / Passport, Academic Transcript, Academic Certificate and CV / Resume. System: creates the application record, student folder, Admission Form PDF and workflow record.
01A
COL + Welcome Email
→
System / IPGS Admission Automatically generates one Conditional Offer Letter (COL), saves it in the student folder and sends a congratulatory welcome email with the COL + Admission Form PDF attached. Any Research Intent or other follow-up item appears as a secondary notice and does not replace the main welcome message. The COL is conditional and is not the final Official Offer Letter / LOA.
02
Consultant / SKY Prospect Setup
→
Academic Consultant / Marketing Receives the new-application notification, creates the Prospect in SKY, returns to the action page, enters the SKY Prospect ID, selects the applicable Fee Group from the live Fee Structure Master and marks Prospect Done. Add Students / admission processing is not done by Marketing.
Admission review continues while SKY Prospect operations are being completed
Document Review→Qualification Screening→SAC→IA / PREREQ if required
03
Document Review
→
Registry Open Applications → Open → Documents. Verify uploaded documents and complete the document review. Use the controlled PG-ADM-01 and regenerate it only when a refreshed copy is required.
04
Qualification Screening
→
Registry Confirm academic field relationship and relevant experience where applicable. AI/document screening may assist review, but it does not replace the authorised SAC decision.
05
SAC Review
→
Registry / SAC Create or select the SAC session, assign eligible candidates, prepare the SAC pack and record the authorised outcome. Current route options include Direct Entry, Internal Assessment and Rejected / Not Qualified. PREREQ is not selected directly as a SAC outcome.
06
IA / PREREQ (if required)
→
Registry / Academic Candidates routed to IA complete Internal Assessment. If the authorised IA outcome requires a prerequisite course, PREREQ is handled after IA. Direct Entry bypasses this stage.
07
Offer
→
Registry Once the approved admission route is complete and the case is eligible, generate and send the Official Offer Letter. The system records the issue status, PDF and timestamp.
08
Electronic Acceptance
→
Student Opens the Acceptance link and signs electronically. System: stores the signed acceptance record and timestamp and updates Acceptance status.
Prospect / Activation rule: this is a separate operational workstream with its own status and controls. Once the consultant has completed the SKY Prospect + Fee Group task, Registry may complete SKY activation and record the relevant SKY Student / Registration ID. Do not invent a cross-module gate that the Prospect / Activation module itself does not require.
09
Registry SKY Activation
→
Registry Open Prospect / Activation. Confirm Prospect Done, activate/register the student in SKY and mark Active in SKY Done. Record SKY Student ID / Registration No. when available.
Orientation rule: Orientation is a session-based operational workstream with its own lifecycle. It does not perform Academic Handover. Main page = monitoring; View Session = processing.
10
Orientation Session Setup
→
Registry Click + Create Orientation Session, create the session, then open it and Add Students. Adding students does not send email automatically. Review the roster, then explicitly click Send Invitation. Automatic reminders apply only to students whose invitation has been sent.
11
Orientation Attendance & Feedback
→
Registry / Student At the appropriate point in the session, Registry opens Attendance. Attendance remains open until staff clicks Close Attendance; there is no timed auto-close. Students may confirm through their personalised link or the session QR. Feedback is completed after attendance confirmation. Registry may manually resolve attendance where necessary.
12
Orientation Recording & Completion
→
Registry End the session, add the recording link and explicitly send the recording. When the completion checks are satisfied, click Complete Orientation. The system locks the completion record and generates the official Orientation PDF report. Completed sessions provide View Report, Download PDF and report revision controls.
Academic Handover rule: Academic Handover is its own module and is not embedded inside Orientation. Main page = monitoring; View Handover = processing.
13
Academic Handover
→
Registry Click + Create Handover Session, open the session, add students and click Handover Now. Academic and the configured IT / Moodle / e-Library PICs receive the handover information. Use the Handover & Communication tab to monitor or resend operational emails.
14
Provisioning
→
PICs / Registry IT completes Innovative Email, Moodle completes LMS access and e-Library completes library access. Registry monitors progress inside View Handover → Provisioning. When all three are complete, the student becomes ready for final access notification.
15
Student Access → ACTIVE STUDENT
✓
Registry Open View Handover → Student Access and send the final student-access email after provisioning is complete. Temporary credentials are not retained as ordinary admission data. Successful access delivery completes the operational student-activation journey.

How to Use the New Session-Based Modules

Monitoring page → processing popup

Orientation

  • Main table shows only session summary, student count, current stage, status and View Session.
  • Overview: session details and headline counts.
  • Students: assigned roster, invitation, attendance, feedback and recording status.
  • Communication: invitation and reminder records.
  • Attendance & Feedback: Open / Close Attendance, QR, manual review and feedback summary.
  • Recording & Completion: recording link, recording distribution, completion checks and official report.
  • Activity: audit trail for the session.

Academic Handover

  • Main table shows handover summary, student count, current stage, status and View Handover.
  • Overview: batch details and headline status.
  • Students: handover roster and each student's current progress.
  • Handover & Communication: Academic email, PDF and PIC task notifications.
  • Provisioning: Innovative Email, Moodle and e-Library status.
  • Student Access: final access notification after provisioning.
  • Activity: handover audit trail.

Fee Structure Master

Single source for agent Fee Group selection
Core rule: do not type or invent a Fee Group outside the master. Academic Consultants select from the ACTIVE list supplied by the Fee Structure module.
  • Fee Group Code is the operational value saved to the Prospect / Admission record.
  • Fee Structure Name is the staff-friendly description.
  • Scope is controlled by Programme + Level + Study Mode + Intake.
  • Intake names are standardised chronologically, e.g. January 2026, May 2026, September 2026.
  • Use ALL only when the structure genuinely applies across that dimension.
  • Fee Components use standard categories: Coursework Fee, Research Fee, Mixed-Mode Fee, Registration Fee and Other Approved Non-Academic Fee.
  • Payment Schedule records the approved payment sequence only. It does not collect money and does not create an invoice.
  • Fee Structure PDF is the approved Drive reference mapped to the Fee Group.
  • ACTIVE = available to agent. INACTIVE = hidden from new selection but historical records remain.
  • A Fee Structure cannot be activated without an accessible PDF.

AI Operations Center

Current capability boundary
  • Displays current operational workload and agent ownership model.
  • Registrar Office Agent is the supervisory layer in the planned agentic architecture.

Troubleshooting & Good Practice

Check these first
  • If figures look outdated, click Refresh.
  • Use Reference No as the main identifier for internal follow-up.
  • Open student folders and generated documents from the applicant record instead of browsing Drive manually.
  • If an applicant cannot be found, clear filters and search by Reference No, ID / Passport or email.
  • Do not treat AI/document screening as the authorised SAC decision.
  • Do not select PREREQ directly at SAC; follow the approved IA route.
  • If a Fee Group is not available to the agent, verify ACTIVE status, PDF and matching scope.
  • In Orientation, Add Students does not send invitation; use Send Invitation explicitly.
  • Attendance stays open until Registry closes it manually.
  • Do not put Academic Handover actions inside Orientation; use the Academic Handover module.
  • Do not mark the student operational journey complete merely because accounts were created; final Student Access must be sent.
  • Completed Orientation records are locked. Use report revision instead of silently changing the completed record.

Recommended UAT

Use controlled test records
Minimum regression check after a system change: test one application journey, one consultant Prospect/Fee Group action, one Orientation session and one Academic Handover session. Confirm module actions, emails, status transitions, popups, PDFs, audit records and ACTIVE/INACTIVE master-data behaviour before treating a new change as production-ready.
